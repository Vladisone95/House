# Apartment design project — agent guide

Interior design workspace for a real 3-room apartment (Vienna Parkside Residence, Bucharest,
type C3). The owner is not a 3D specialist: explain in plain language, show images, and **ask
before guessing** any dimension, orientation or layout fact (see "Asking the owner").

Current phase: **iteration 2 — furniture variants**. The shell is done (rooms, walls,
windows, doors with swings, sun). Furniture lives in variants (`data/variants/<KEY>.toml`), every
piece has a readable id like `A.sofa-living-1` (ADR 0005). Variant A is empty - plan pieces with
the owner before adding them. Variant **DEV** = the developer's furnished render recreated (ADR 0006).
Storage pieces (wardrobes, cabinets, nightstands, vanities...) open in Blender and have modules
(`DEV.wardrobe-living-1/m2`) with designable interiors (shelves/rails/drawers - empty until the
owner asks). **Fixed service points** (`[[fixed_points]]`: sinks' water, WCs, MSR washer, hood
vent) and the fixed entrance bind every variant - a sink/WC/washer/hood must sit on its point.
**Built-ins** (`[[built_ins]]`, e.g. the 180 L boiler over the washer) appear in every variant;
a variant can tile its own floors/walls per room with `[rooms.<id>]` (ADR 0009), or paint them
(`paint = "#rrggbb"`). **Style variants** (`style_of = "V1"`, ADR 0011) restyle a layout - same pieces and
places, other colours/finishes; the add-on lists them in a *Style* dropdown under the layout buttons.
Never move a piece in a style variant - edit the layout, then regenerate its styles.
**Every design must pass `docs/design-rules.md`** (ground rules for a good home + checklist). The owner can recolour
pieces / rooms in Blender (*Colours...*, *Room colours...*) - those picks land in `owner_colors`; keep them.

## Golden rules
1. **`data/apartment.toml` is the single source of truth.** Every object in
   `models/apartment.blend` is generated by `blender/build_scene.py`. Never hand-model or
   hand-edit generated geometry (in Blender, via MCP, or by editing the .blend). Change the
   TOML or the build script, then rebuild.
2. **Validate before you build.** `uv run apartment validate` must say `OK`
   (a PostToolUse hook re-runs it whenever `data/` or `src/apartment_core/` is edited).
3. **Every number has a provenance.** When a value changes, update its `status`
   (`estimated` → `confirmed` → `measured`) and log why in `docs/decisions/` (ADR style).
   Never silently change an owner-confirmed value (list in @docs/decisions/0001-layout-reconstruction.md).
4. **Verify visually.** After a build, render (`uv run apartment render --views plan,...`)
   and look at the PNGs before claiming success. Report what you saw.
5. `apartment_core` stays **pure Python** (no `bpy`, no numpy) — it runs in CPython, in
   Blender, and in tests. Blender-only code lives in `blender/`.

## Coordinate system & orientation (memorise)
- Metres. Origin = outer corner of facade B and the bottom neighbour wall. +X along facade A,
  +Y towards facade A, Z=0 finished floor, ceiling 2.70 m.
- **Facade A (+Y) faces WNW (bearing 294°)**: living window W1, bedroom-1 window W2.
- **Facade B (−X) faces SSW (204°)**: balcony door, kitchen W3, bedroom-2 W4. Balcony projects to −X.
- `site.plus_y_bearing = 294` drives everything sun-related. North in model = (0.914, 0.407).

## Working with Blender
- Prefer **headless scripts** (`uv run apartment build/render`) — reproducible, reviewable.
- **After every build, refresh the owner's open Blender** via the MCP (reload the add-on modules +
  `wm.revert_mainfile`), or start it with `uv run apartment open` if it is closed. Never leave the
  owner looking at a stale file or old add-on code.
- **Light rules (ADR 0008, all variants)**: no light/probe/camera gizmos in 3D views (Overlays >
  Extras off); new fixtures get no shadows unless a statement pendant; keep cut-off distances;
  inactive variants stay excluded from the view layer.
- The **Blender MCP** (`.mcp.json`, server `blender`) controls the owner's *open* Blender for
  inspection, screenshots and quick experiments. Follow the `blender-mcp-workflow` skill.
  Anything worth keeping must be ported into the TOML/build script.
- The globally installed **Bonsai/IFC skills do not apply** to this project (plain Blender
  geometry). Don't use `bim.*` operators unless the owner explicitly asks for an IFC export.

## Asking the owner
Ask (AskUserQuestion) when a dimension, orientation, room function or opening position is not
derivable from `data/`, `docs/decisions/` or the developer plan. The terminal does not render
ASCII diagrams reliably — **show layouts as images** (write a PNG, open it with
`cmd //c start "" <file>`), then ask. Offer a recommended option and say what each choice changes.

## Conventions
- Python 3.12+ style, `ruff` clean, type hints, small pure functions; tests for core logic.
- Object names in Blender: `WALL_<id>`, `FRAME_/GLASS_<opening>`, `PLAN_<opening>`, `FLOOR_<room>`,
  `CAM_<room>`, `LABEL_<room>`, `FURN_<furniture id>`; collections `Walls, Floors, Ceiling, Openings,
  Balcony, Structure, Context, Annotations, Furniture (> Variant A, B...), Cameras, Lighting`.
  Custom props carry ids (`wall_id`, `room_id`, `opening_id`, `furniture_id`, `variant_key`).
- Storage parts: `FRONT_<id>_<m1-door-left-1>` (origin on the hinge), `INT_<id>_<m2_shelf-1>`; props
  `part_id` (`<id>/m2/shelf-1`), `motion`, `amount`. Plan markers `FIXED_<point id>`.
- Never move a fixed point (pipes/vents) to suit a layout without asking the owner - it is a shell fact.
- Furniture ids are the owner's handle: never change one silently; if a piece changes room/type,
  rename it and tell the owner the new id.
- Commit only when the owner asks. Never commit `models/*.blend` or `renders/`.
- No real personal data in docs/examples; the owner's apartment number is fine.
